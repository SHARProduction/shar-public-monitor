# Публичный монитор SHAR Production

Open-source инструмент для black-box проверки публичного сайта [SHAR Production](https://sharprod.com/) и публичного MCP endpoint `https://mcp.sharprod.com/public`. Используются только встроенные возможности Node.js 24. Инструменту не нужны исходники production-сайта, приватный snapshot знаний, реквизиты доступа, сборка, полный crawl или доступ к деплою.

Репозиторий задаёт проверки и расписание GitHub Actions. Само наличие файлов не доказывает, что расписание включено, workflow выполняется успешно или уведомления доставляются. Текущее состояние нужно подтверждать по публичным запускам workflow и фактическим ответам endpoint.

## Объём проверок

- Режим `fast` проверяет главную и контактную страницы, защиту lead endpoint, sitemap, robots, публичную discovery lineage, MCP discovery, handshake, список из 15 read-only tools, три детерминированных вызова и ожидаемый контракт Official Registry.
- Режим `full` дополнительно вызывает остальные 12 инструментов, чтобы за проход проверить все 15.
- Каждый запрос ограничен таймаутом 15 секунд и телом 1 МиБ. Redirect не следует автоматически.
- Неуспешный проход подтверждается одним полным повтором. Устойчивый сбой завершает процесс кодом `2`.
- Отчёт не сохраняет полные тела ответов. Он содержит статусы проверок, публичные URL, выбранные заголовки, lineage и длительности.

Количество инструментов, версии протокола, хеши lineage и Registry-условия являются ожидаемым контрактом проверки. Их наличие в коде не является утверждением о текущем состоянии публичного сервиса.

## Запуск

```bash
npm test
node scripts/monitor.mjs fast
node scripts/monitor.mjs full
```

В workflow настроен быстрый запуск на минутах 7, 22, 37 и 52 каждого часа UTC, а полный — ежедневно в 03:43 UTC. GitHub может задерживать scheduled jobs или отключать их после неактивности. Только фактический event типа `schedule` подтверждает scheduled execution.

Режимы `fixture-failure` и `fixture-recovery` не обращаются к endpoint и используют отдельные TEST markers. Они предназначены для проверки incident/recovery логики и не должны менять production incidents.

## Инциденты и ограничения

После подтверждённого сбоя alert job может создать или обновить GitHub issue. Для этого он использует только repository `GITHUB_TOKEN` с `issues: write`; check job имеет `contents: read`. Доставка уведомлений зависит от настроек подписки GitHub. Сбой инфраструктуры до создания отчёта может оставить только failed workflow run без issue.

Монитор проверяет только доступные извне ответы. Он не подтверждает состояние панели владельца, сам факт деплоя, приватную аналитику, доставку уведомлений или происхождение runtime image.
